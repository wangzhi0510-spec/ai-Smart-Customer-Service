# AI 使用说明与人工审查

## 1. 使用范围

开发过程中使用 AI 工具辅助需求拆解、接口草拟、测试设计、代码审查和文档整理。AI 只提供候选方案，不能替代需求标准、人工验收或安全审查。

第一标准始终是《AI开发工程师笔试题.docx》，其次是批准的系统设计和实施计划。实现决策必须回到代码、测试输出和运行契约核对。

## 2. AI 参与的工作类型

- 将原始需求拆分成可验证任务和阶段检查点。
- 生成 API、数据库、RAG 和 Docker 设计草案。
- 为认证、文档状态机、检索过滤、SSE 顺序和用户隔离补充测试案例。
- 辅助定位 Vue runtime template、Vitest 扫描 Playwright 文件等真实缺陷。
- 整理中文项目文档、评测数据和部署步骤。

## 3. 人工审查清单

每次 AI 产生代码或文档后，人工执行：

1. 对照笔试文档逐条检查是否遗漏强制功能。
2. 检查 API 路由、字段、状态码和 SSE 事件是否与实现一致。
3. 检查数据库外键、唯一约束、时区和删除生命周期。
4. 检查 RAG 是否真的经过 Dense、Sparse、RRF、父块、重排和证据 Prompt。
5. 检查第二阶段功能是否被错误描述为首版已实现。
6. 运行定向测试、全量测试、构建、Playwright 和 Compose 配置检查。
7. 扫描 `.env`、API Key、JWT 密钥、Token、模型权重、日志和构建产物。
8. 查看 Git diff 和提交边界，拒绝无关格式化和未经授权的外部写入。

## 4. 数据和隐私边界

不向 AI 工具提供真实用户上传文件、真实对话、生产 Token、API Key、数据库密码或模型权重。评测使用仓库内合成中文样例。日志和提示词不得包含敏感信息。

## 5. 可追溯性

每个实现切片先测试后编码，验证通过后独立提交；任务状态记录在 `tasks/todo.md`。重要架构取舍记录在批准设计文档和后续 ADR 中，远程提交通过 GitHub 工具回读核验。

## 6. 已知限制

AI 生成的测试可能过度依赖 mock，因此真实基础设施联调仍需在目标环境执行。离线 RAG 评测用于回归和契约验证，不等价于真实 LLM 的事实性或 RAGAS 分数。
